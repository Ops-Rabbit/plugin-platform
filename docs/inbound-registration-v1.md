# Host-owned Inbound registration controls v1

SDK/CLI 0.30.0 adds declarative business configuration for a host-owned source Inbound registration control. The host owns the create/edit screen, saved Inbound identity, registration checkbox, availability, tenant-admin authorization, grants, enablement timestamp, durable delivery, retries, retention and audit. Generated-output Manage access remains a core feature on every Inbound family without requiring this capability or any resource plugin.

A plugin declares `capabilities.inboundRegistration` with `schemaVersion: "1"`, one declared `resourceKind`, supported `sourceProviders`, localized `labelKey`/`descriptionKey`, and optional business configuration. It requires matching `resourceRecords`, `inboundLifecycle` and localization capabilities. Unsupported hosts reject the declaration. Declaring it does not enable registration or grant access.

Optional `configuration` references declared tenant-admin actions: a read-risk `readActionId` and write-risk `writeActionId`. The host renders the declared bounded `boolean`, `text` and `json` fields with defaults and localized keys. These fields cannot replace core controls such as `enabled`, grants, tenant/owner identity or retention policy. They describe business mapping, profile and enrichment choices only. They contain no credentials or secrets. CLI validation verifies these localization keys in every declared locale.

The read action accepts `PluginInboundConfigurationRequestV1` (`inboundId`) and returns `PluginInboundConfigurationV1`: `inboundId`, current `incarnationId`, host binding `revision` (zero when absent), and exactly the declared `values`. The write action accepts that same snapshot shape. It validates business semantics, then uses a configuration transaction to save immutable mapping/profile history with the new binding revision. Use `expectedRevision` and `expectedIncarnationId` in `bindSourceInbound`; the host checks both under its source/binding locks. A concurrent edit, toggle or deletion/recreation rejects the whole transaction, not just the host metadata update.

Plugins with this declaration must preserve the host's live `enabled` value when requesting `bindSourceInbound`. The host rejects a plugin attempt to change it; only the host-owned checkbox endpoint changes enablement. Configuration writes can occur while registration is off. The first enablement boundary is host-stamped, and disabling/re-enabling starts a new eligible intake epoch. Plugin mapping history must remain immutable and resolve the configuration applicable to an event's captured revision, including core-only toggle revisions.

The host must enforce tenant-admin authority for catalog discovery, read and write actions and toggling. It validates action responses before rendering them, bounds complete request/response bytes (at most 64 KiB), and revalidates effective plugin generation/enablement and source provider/incarnation. It also enforces no persistence before canonical or outbox content writes. SDK validation does not implement those host boundaries or establish lifecycle readiness.

See `packages/plugin-sdk/reference/inbound-registration.mjs` for executable atomic configuration ordering. Existing plugins without this declaration keep their prior public binding contract. Core output grants and incident record grants remain independently authorized; a business configuration action cannot substitute for either.
